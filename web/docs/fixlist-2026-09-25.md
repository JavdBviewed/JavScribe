- 卡死点定位（09-25 17:3x-18:2x 专项排查，DVMM-299 / MIDA-574-破解）：
  1. 快照：主线程 `State=S wchan=futex_do_wait`，21 线程全睡眠，**非磁盘 IO
     阻塞**（D 态/io 阻塞特征均无）；
  2. 整文件顺序读取：7.33GB/36s、6.35GB/11.5s，无任何 >5s 慢块；dmesg 无
     I/O error → 盘与文件数据层健康；
  3. 音频流体检：456628 包全均匀（21.33ms/包），3080-3130s 区域无任何跳变/
     异常包；卡死位置 ±15s 切片单跑 0.5s 秒过 → 触发条件不是局部坏包，而是
     「处理到约 3091s（DVMM 32%）/ 8885s（MIDA 98.9%）的历史上下文」；
  4. A/B：默认线程 vs `-threads 1` 单线程 → 两种都在同位置短暂停滞（20s~
     数分钟，futex 睡眠）后**自恢复**，均 exit 0 完成 → 非解码线程竞态；
  5. 手动单文件重跑：78.6s 全过无卡顿（120x 实时）；应用内 4 次重提取全卡死
     ——共同点：应用内是 **DVMM+MIDA 双 ffmpeg 并行**（extract_workers=2，
     2×21 线程 > 24 核，过度订阅），手动都是单 ffmpeg → 判定为并发争抢下的
     间歇性 futex 长停顿（可自恢复，但 4 次均 >120s 窗口）。
- 缓解（0.2.19）：卡死判定后自动重试（新进程重提取，默认共 3 轮）；单轮失败
  不再需要人工介入，多轮后仍卡死才标 error（报错带已重试次数）。
- **最终根因（0.2.20 修复，09-25 19:2x 决定性 A/B）**：DVMM-299 的 AAC 音轨含
  损坏段，ffmpeg AAC 解码器按 `-loglevel error` 正常输出解码错误 —— 全片累计
  **约 30MB stderr**（`channel element 2.3 is not allocated` / `Invalid data found`
  刷屏）。`extract_audio_progress` 用 `stderr=PIPE` 却从不消费：
  64KB StreamReader 流控缓冲 + 64KB OS 管道写满后 ffmpeg 阻塞在 `write(2)` 上，
  整个进程冻结（无 CPU / 无 progress / 无写入）→ 活性检查 120s 判死锁。
  卡死点恰好是损坏段开始解码的位置（DVMM 3211s=33%、MIDA 8885s=99%），
  与文件内容强相关，故确定性复现、重试必然同点再卡。
- 决定性 A/B（同机同文件同 ffmpeg 二进制）：
  | 变体 | 结果 |
  |---|---|
  | 现行实现（stderr PIPE 不消费） | **7/7 冻结**于 3211s（含 0.2.19 部署后全部重试） |
  | 现行实现 + stderr 排水任务 | **3/3 完整跑通**（74-79s，stderr 收满 30,445,066B） |
  | 现行实现 + stderr=DEVNULL | **1/1 完整跑通**（76s） |
  | 裸 ffmpeg + shell 读 progress（stderr 走终端） | 2/2 完整跑通（先前排查） |
- 此前「并发争抢/IO/坏包/线程竞态」假设全部排除（见上 17:3x 排查记录第 1-4 条），
  但「应用内卡死」与「手动跑通」的真正差异是 **progress 管道的读取方背后
  stderr 有没有人排空**，而非读取方式本身（无 wait_for 的纯 readline 同样冻结）。
- 修复（0.2.20）：`extract_audio_progress` 增加 **stderr 专用排水任务**
  （持续 `read(65536)`，环形保留尾部 8KB 供报错）；kill/cancel 路径防御性
  cancel 排水任务；正常结束等待排空收尾。活性检查（0.2.18）与自动重试
  （0.2.19）保留作兜底（其它真死锁仍可被识别/自愈）。
- 回归测试：`tests/test_audio.py::test_stderr_flood_does_not_deadlock`
  （假 ffmpeg 打 369KB stderr 洪峰 + progress，无排水将超时失败）与
